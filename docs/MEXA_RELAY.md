# Internet relay for MEXA measurements

For a temporary connection test without a third PC, use **Host temporary relay
on this PC** in the flow-controller app. It runs a loopback relay and an outbound
Wormhole tunnel (or optional Cloudflare Quick Tunnel). The analyser bridge uses Internet relay mode. Follow
[temporary relay setup](MEXA_QUICK_TUNNEL.md); the separate-server instructions below
are not needed for that option.

## Separate server option

The analyser PC and flow-controller PC both make outbound connections to a
separate relay. Neither opens a listening port in relay mode. They do not need
to reach each other's eduroam addresses.

This repository includes the relay server and both clients, not a hosted service.
Before using it across the internet, arrange an approved server, a hostname and
a valid TLS certificate. UCL must permit outbound WebSocket connections to that
endpoint. No firewall, network policy, hosting account or DNS changes are made
by the apps or installers.

## Set up the two PCs

If the installed bridge already offers **Internet relay (outbound WSS)**,
including the 28 August Wormhole package, it remains compatible with this
flow-app update. Keep that installation. For a bridge predating relay support,
extract a new package and run `install_mexa_bridge.bat` to install the WebSocket
dependency. On the flow PC,
rerun its installer or install the updated `requirements.txt` into the existing
app environment. Restart the apps when safe for the rig.

Ask the relay administrator for its URL and the two role keys below. Do not
paste credentials into a URL, experiment notes, screenshots or support logs.

| Setting | Analyser PC bridge | Flow-controller MEXA tab |
| --- | --- | --- |
| Connection mode | Internet relay (outbound WSS) | Internet relay (outbound WSS) |
| Relay URL | `wss://your-relay-hostname/mexa` | Exactly the same URL |
| Relay access key | Publisher key | Receiver key; different from publisher key |
| Shared key | Generated by bridge; use Copy key | Copy the bridge's current shared key |

The analyser shared key is a third, independent key. Do not supply it to the
relay administrator or reuse a relay access key for it. The bridge generates a
new shared key each time its window launches. Keys are held in application
memory, not saved in preferences or measurement logs. Enter them again after
relaunching. Treat the clipboard as sensitive after copying a key.

The IPv4 and TCP-port boxes are disabled in relay mode. They are only used by
Direct LAN. On the analyser PC, select the COM port and choose local logging as
usual. Start with **Simulation only** to test the route without instrument I/O.
Click **Start reader and stream**, then **Connect MEXA** on the receiver.

The status first reports relay connection, then waits for the other PC, then
reports shared-key authentication. New samples should follow. If one PC has
not connected, the other can remain connected and waiting. Nothing changes the
analyser's mode or burner settings during connection or reconnection.

Local source logging remains optional. Enable it if you need a record during
internet outages. Receiver logging is independent and still required for live
optimiser capture. All reported channels, alarms, quality flags and raw replies
use the same record format as Direct LAN. Fresh out-of-range values are streamed
and logged as invalid; they are never accepted by the optimiser.

## Deploy the separate server

For the CachyOS home-host package, start with `CACHYOS_START_HERE.md` at the
ZIP's root. It includes small install/start scripts, private key storage and
an optional user service. It still requires public HTTPS reachability; the
program cannot configure an ISP's upstream NAT.

Use an approved VM or a container service that supports long-lived WebSockets.
Run exactly one server process/replica per analyser/receiver pair. This version
has no shared state between replicas and accepts one connection for each role.
Do not enable autoscaling or route the two clients to different replicas.
Prefer an always-on service: sleeping services cause connection interruptions.

### Python service on a VM

Extract the relay-server ZIP on the server. It needs Python 3.11 or newer and
only the dependency in `requirements-relay.txt`, not Qt, serial drivers or the
flow-controller application. Run from the extracted package root:

```text
python -m venv .venv
```

Use that environment's Python for the following commands (`.venv/bin/python`
on Linux or `.venv\Scripts\python.exe` on Windows):

```text
python -m pip install -r requirements-relay.txt
python -m mexa_bridge.relay_server --generate-keys
```

The second command prints two fresh keys once. Store them in the server's
secret manager or a restricted service environment, under these exact names:

```text
MEXA_RELAY_PUBLISH_KEY
MEXA_RELAY_RECEIVE_KEY
```

Do not store keys in source control or pass them as command-line arguments.
Do not run key generation on every server restart: the PCs need stable role
keys until you deliberately rotate them. The two keys must be different,
32–128 printable ASCII characters, with no spaces. Generated keys meet this.

Start the backend on loopback, with those environment variables available to
the process:

```text
python -m mexa_bridge.relay_server --host 127.0.0.1 --port 8765
```

Use an approved HTTPS reverse proxy on that same server to expose `/mexa` on
port 443 and forward it to `127.0.0.1:8765`. A Caddy template is supplied at
`deploy/mexa-relay/Caddyfile.example`; replace its example hostname with your
real DNS name. Your administrator must provision DNS, TLS and the server's
firewall, and configure the relay/proxy to restart after a server reboot.
Keep port 8765 private. Caddy supports WebSocket upgrades through
[`reverse_proxy`](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy).

If your administrator manages certificates directly, the Python server can
terminate TLS itself:

```text
python -m mexa_bridge.relay_server --host 0.0.0.0 --port 8443 --cert /path/fullchain.pem --key /path/privkey.pem
```

Use the corresponding `wss://hostname:8443/mexa` URL. Port 443 is preferable on
restricted networks; arrange it through the server's approved front end.
Certificate renewal/reload remains an administrator task. A non-loopback
plaintext bind is refused unless `--behind-tls-proxy` is explicitly selected
for a private backend.

### Container hosting

`deploy/mexa-relay/Dockerfile` packages only the relay modules. Build from the
repository root or extracted relay-server package root:

```text
docker build -f deploy/mexa-relay/Dockerfile -t mexa-relay .
```

Configure the hosting service's private target port as 8765, set the two keys
as runtime secrets, and enable its HTTPS/WebSocket front end. The container
runs unprivileged and does not need a writable volume. Do not publish its
plaintext port directly on the internet. If using Docker on the same VM as
the HTTPS proxy, publish the backend to loopback only, for example
`-p 127.0.0.1:8765:8765`. The image's explicit `--behind-tls-proxy` flag assumes
you supply that protected front end; it does not add encryption itself.

`https://your-relay-hostname/healthz` returns a short health response without
credentials or measurements. This proves only that the relay process is
reachable, not that either PC is connected or the analyser is ready.

## Security and reconnect behaviour

Internet clients require `wss://`, check the server certificate and hostname,
and do not offer a certificate-verification bypass. TLS encrypts each PC's
connection to the relay. The relay terminates TLS and can see forwarded data;
this is not end-to-end encryption from PC to PC. Use an approved operator.
[WebSocket TLS documentation](https://websockets.readthedocs.io/en/15.0.1/howto/encryption.html)

Separate role keys restrict who can publish and receive. The two PCs also
authenticate each other with their analyser shared key. Each new connection
pair uses a fresh receiver challenge and HMAC-SHA256 sample signatures, so a
record from a previous session cannot be replayed as a new measurement. The
server has no serial or burner-control code and rejects command messages.
MEAS/STANDBY remain confirmed local actions in the bridge.

The server does not save measurements. It bounds message sizes to 16 KiB,
accepts at most eight protocol messages per second per connection, limits
pending clients and disconnects stalled sends. These are application limits,
not protection against an internet-scale denial-of-service attack. Configure
appropriate connection/rate limits at the hosting front end. Browser-origin
connections are refused. Do not enable packet/frame debug logging on the host
or proxy; authentication frames contain role keys.

Clients use the operating system's configured proxy where supported. A SOCKS
proxy may need the optional `python-socks[asyncio]` dependency, which is not
included. Ask IT for the approved route if proxy connection fails; do not
disable certificate checks. [Proxy documentation](https://websockets.readthedocs.io/en/15.0.1/topics/proxies.html)

After an outage, clients retry with a bounded delay up to 15 seconds. A peer
disconnect closes the pair, requiring a new handshake. The bridge keeps one
latest value for transport and sends only readings acquired after pairing;
it does not upload saved logs or replay an outage backlog. Readings can be
lost between PCs during interruption. Enabled source logs retain them locally.

Sequence gaps, duplicate records, changed sources, stale/future timestamps,
authentication failures and disconnects interrupt live capture. Normal
five-second freshness limits and one-second future-clock tolerance still
apply; internet mode does not relax them. Resettle and start a new live window
after recovery. Reconnection never changes flows or resumes an experiment.

Rotate compromised role keys at the server and on the affected PCs, then
restart the service to disconnect existing sessions. Stop/restart the apps to
change connection fields. Update the separate shared key on both PCs if it
has been exposed.

## Troubleshooting

- **Cannot reach relay:** check hosting, the URL, DNS, certificate, and outbound
  WSS access to the relay on port 443. An eduroam peer-to-peer exception is not
  needed for this design, but outbound access must still be permitted.
- **Relay access denied:** use the publisher key on the analyser PC and the
  receiver key on the flow PC. These are not the analyser shared key.
- **Role already connected:** stop the other copy using that role. The server
  does not silently replace an existing connection.
- **Waiting for the other PC:** confirm both use the same relay URL and that
  hosting runs exactly one replica.
- **Shared-key authentication failed:** copy the key from the current bridge
  window into the receiver. A bridge relaunch generates a new shared key.
- **Certificate verification failed:** correct the relay's certificate/chain,
  hostname or PC clock. Do not use an insecure override.
- **Stale/future samples:** synchronise PC clocks and investigate latency or
  suspended applications. Do not extend the age limit to accept delayed data.

For a same-PC simulation test, run `run_mexa_relay_local.bat` on Windows, or
`python -m mexa_bridge.relay_server --local-test`. It prints temporary
publisher/receiver keys and starts on `ws://127.0.0.1:8765/mexa`. Enter those
keys and that URL in the apps on the same PC. Keep its console open; Ctrl+C
stops it and invalidates the temporary keys. It is not reachable from another
PC, does not change the firewall and is not installed as an auto-start service.

The clients allow unencrypted `ws://`
only for numeric loopback addresses. This is not an internet deployment test.
Then repeat simulation through the deployed WSS URL before connecting the
real analyser. [Instrument validation and optimiser workflow](MEXA_SETUP.md)
